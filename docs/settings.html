Settings

Your settings

  • A setting missing from a file takes its default, and every feature starts off.
  • Edit settings on the Settings page of the web interface, in the files of config/, or with /settings set from Telegram or Discord. Each value is checked before it is saved.
  • A profile shares settings between accounts, or changes them for a few hours.
  • Secrets (e-mails, passwords, tokens) are write-only and live in secrets.json.
  • Each account signs in as its own simulated PC, drawn once and kept.

Defaults

A setting missing from a file takes its default. Every feature and every Active option is off, and lists and coordinates are empty. Other values, such as intervals and thresholds, are the recommended ones.

"Reset to default" removes the key from the file. The web interface always shows the value the bot really uses.

Turning a feature on or off from the Map, the Deck or the bots does not change these settings: that choice is kept in data/<instance>/overrides.json. Writing the feature's Active setting ends it. See Turning a feature on or off.

Four defaults are not what you might expect: Expeditions.PrimaryToKeep and Expeditions.MinPrimaryToSend are 0, General.Proxy.LoginOnly is false, WebUI.Enable is true, and Brain.Boosters.Active is true: with the Brain on, TGoat proposes booster activations.

Example: this instance file turns one feature on and sets one number. Everything else is default.

"Settings": {
  "AutoFarm": { "Active": true, "MinimumResources": 500000 }
}

A changed meaning, settings that do nothing yet, changed defaults, zone checks (4)

One setting changed meaning: AutoFarm.CombatPlanner.MaxFailureProbabilityPercent (1%) is the risk of losing a ship that an attack may carry. It also sets the last check before sending: 773 simulated battles of the fleet that leaves, at most 3 with a ship lost.

Two settings change nothing yet, whatever their value: Defender.Autofleet.UseJumpGate (not used yet) and Defender.Autofleet.ExpeditionAsLastResort (not used yet). Their help on the Settings page says so. General.ExchangeRate is read only by the production settings of AutoMine. Everything else values resources at 2.5 : 1.5 : 1, the boosters at 3 : 2 : 1 and the offer of the day at the trader's rates. AutoFarm.MaxDefensePoints and MaxFleetPoints count resources, the cost of the defences or ships, as in TBot, not game points.

Some defaults changed too, such as Brain.AutoMine.MaxDaysOfInvestmentReturn (60 days) and Expeditions.MaxExpeditionsPerOrigin (0, no limit). The full list is under Changed defaults. A value you wrote stays.

Colonize zones are checked when you save them. Systems or positions in the wrong order, and 0 planets wanted, are refused. A zone cannot cross the end of the galaxy: split it in two.

Fleet-save options

Whatever the options, a fleet-save never goes to one of your planets or moons that a hostile fleet targets: the fleet would land there before the attack, or just before it, and would not leave again. If that leaves no destination, a warning says which ones were skipped, then the usual last resorts run. The last resort, the moon or planet at the same position, leaves DeutToLeave behind like any fleet-save.

The Defender's fleet-save has five options. Their defaults keep the fleet-save of TGoat 0.1.0-alpha.1, except the recall moment, which is now drawn at random.

Three ways to edit

  • The Settings page: forms, a raw JSON editor and a History tab.
  • A text editor: edit the files in config/. TGoat notices the change and applies it.
  • Telegram or Discord: /settings get, /settings set and /settings undo.

All three go through the same writer. Each value is checked before it is saved, and an unknown key gets a suggestion such as "did you mean Active?". TGoat keeps your comments, layout and key order, and never rewrites your files on its own.

Example, from Telegram:

/settings set AutoFarm.MinimumResources 500000
/settings undo

The first command is checked and applied at once, even if the instance is offline. The second puts the old value back.

If a file changes while you edit it in the web interface, your edits are merged setting by setting. When you both changed the same setting, you choose which value to keep.

Profiles

A profile is a file in config/profiles/ that holds settings only, never account data or secrets. Any instance can use it.

  • Base profile (Profiles.Extends): applied under the instance's own settings, so the instance wins. Use it for what several accounts share.
  • Active profile (Profiles.Active): applied over the instance's settings.

Both lists are saved in the instance file, so they survive a restart. Editing a profile reloads the instances that use it.

Example: config/profiles/night.json turns farming on and attacks only larger loot.

{
  "Version": 2,
  "Description": "Quiet night farming",
  "Settings": {
    "AutoFarm": { "Active": true, "MinimumResources": 2000000 }
  }
}

To use it for the next 4 hours, send /profile load night 4h. When the time is up, the instance goes back to its own settings. /profile reset ends it earlier.

Sharing profiles

You can give a profile to another player, and take one, as a code, as a file, or through the Community library.

What is shared: the profile's settings that differ from the defaults. Export an instance and you share its current settings the same way, never its name.

Places instead of coordinates: a coordinate never leaves your computer. Each celestial a profile names becomes a place, A, B, C… (10 at most), with its type (planet or moon) and the settings that use it, such as "AutoFarm: Departure points". You can add a short note to each place, such as "my main moon". A range of AutoFarm.ScanRange becomes "50 systems around place A" when it contains a place; an excluded system of AutoFarm.Exclude is shared when it is a place's own system. Other ranges and excluded positions stay home.

What never is: colonization zones, sleep and wake-up times, trusted players, messages to attackers, titles and Discord names, which notifications go to Telegram or Discord, and anything of the account: e-mail, passwords, tokens, proxy, device, Telegram and Discord settings. The export lists what it leaves out, and refuses a name, description, author or note that holds coordinates.

  • Code: one line that starts with TGOAT1-. A code that was cut or changed is refused. Over 24 KiB, use the file.
  • File: <name>.tgoat-profile.json, plain JSON, 64 KiB at most.
  • Chat: /profile export <name> sends the code; a long one comes as a file.

Import: paste a code or choose a file, pick an instance, and read the preview before anything is written. For each place, pick one of your planets or moons: TGoat suggests one (a moon for a moon; for a departure, the one with the most ships; for a destination, the planet with the most storage; else your main planet or its moon). "Leave automatic" keeps that setting empty, and the preview says what will not work as the author meant. Only your own planets and moons can be picked; until TGoat has read the account, places can only stay automatic. A name or description that cites coordinates is not kept: the profile gets "Imported from" and the name instead. The preview shows each setting the profile would change on that instance, what is left out and why (unknown in this version, personal, a secret, a value out of range), a warning when the profile was made for another class or other universe speeds, and what the setup assistant would change for this account. Import then creates a new profile; your instances stay as they are unless you tick "use it now". To undo, delete the profile.

Community library: browse, search, vote, report and publish, with no account. TGoat contacts it only when you open the Community view or click something there. Your TGoat signs what it publishes with its own key, kept in secrets.json; the web interface shows its short fingerprint as your publisher id. Anyone can download what you publish, so keep your in-game name out of the name, description and author. You can update or delete your own profiles. A profile reported by 3 different players is hidden until the library's owner looks at it. Limits a day: 5 publications or updates, 50 votes, 10 reports; votes and reports work from the day after your first publication or vote. Community.Mode Off turns all of it off.

Secrets

Secrets are write-only. You can set, replace or clear one, but never read it back. The web interface, Telegram and Discord only say whether it is set.

They live in secrets.json, which the web interface never serves. The web interface password is kept there too, as an Argon2id hash under WebUI, never the password itself. Example: in secrets.json, the e-mail and password of an instance sit under its id.

"Instances": {
  "vega": { "Email": "you@example.com", "Password": "…" }
}

Simulated device

Each account signs in as its own PC: a current Windows or macOS computer with Chrome or Edge, your computer's time zone (or the universe's country behind a proxy), and the universe's language. TGoat draws it once, when the instance is created, and keeps it, like one real PC.

The values are in the instance file, under Credentials.DeviceConf, where you can read them. The browser version moves forward by itself over time.

To get a new device, remove the device folder, data/<id>/device/tgoat-<id>, while TGoat is stopped. Editing the values alone changes nothing. Gameforge will see a new PC: if it asks for a check at the next login, sign in with your browser.

Managing instances

Each instance is one file in config/instances/. Adding a file adds the instance, and removing it removes the instance, without a restart.

  • Add: the Instances page, or tgoat setup.
  • Disable: set "Enabled": false in the instance file, use the Instances page, or send /instance disable vega.
  • Remove: the file goes to config/history/removed/ and its secrets are erased. Its folder in data/ stays unless you ask otherwise.

On a single-planet account, TGoat uses the only celestial as origin without writing it in your file. When a second celestial appears, a warning asks you to set the origins.
